Web Cache Poisoning

Learn how attackers manipulate cached responses and cause other visitors to receive unexpected website content.

OWASP A05 CWE-436

01. What It Is

Web Cache Poisoning occurs when an application uses untrusted request data to generate a response that is stored in a shared cache. Other visitors may then receive the manipulated response instead of the correct website content.

OWASP Category: A05 - Security Misconfiguration

CWE: CWE-436 - Interpretation Conflict

02. The Line

VULNERABLE CODE

function vulnerableRequest(request) {
    const key = "/home";
    const host = request.headers["x-forwarded-host"];
    const response = {
        page: "TechStore",
        canonicalUrl: `https://${host}/home`,
        message: "Welcome to TechStore"
    };
    cache.set(key, response);
    return response;
}

Vulnerable Line: The application uses an untrusted HTTP header to generate a URL inside the response without validating it. The cache may then store that response.

The cache uses the same key for the homepage. If the response changes based on a request value, the cache must handle that difference correctly.

04. Why It Matters

A poisoned response stored in a shared cache may affect multiple visitors who request the same cached page.

Possible Impacts

Misleading Content

Visitors may see incorrect information or links instead of the original website content.

Website Reputation

Users may lose trust in a website if they receive unexpected or manipulated content.

Multiple Visitors

One poisoned cached response may be delivered to several visitors.

Example Scenario

Imagine an online store called TechStore. If a manipulated response is stored in its shared cache, another visitor may receive incorrect links or content when opening the same page.

05. The Fix

FIXED CODE

function fixedRequest() {
    const host = TRUSTED_HOST;
    const key = "/home";
    const response = {
        page: "TechStore",
        canonicalUrl: `https://${host}/home`,
        message: "Welcome to TechStore"
    };
    cache.set(key, response);
    return response;
}

Solution: The application uses a trusted host configured by the application instead of accepting an arbitrary host value from the request.

Prevention Methods

1. Validate HTTP Headers: Do not blindly trust values received from HTTP headers.

2. Use Trusted Host Values: Use a configured and trusted hostname instead of accepting arbitrary host values.

3. Configure Cache Keys Correctly: Make sure the cache key accounts for request values that can change the response.

4. Avoid Caching Unsafe Responses: Do not cache responses containing sensitive or user-specific information in a shared cache unless they are handled safely.
