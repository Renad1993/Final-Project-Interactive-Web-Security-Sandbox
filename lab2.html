Weak Random Token Generation

OWASP A02:2021 CWE-330 | CWE-338

What it is

Applications use secret tokens for password resets, session IDs, invitation codes, and API keys. These tokens must be unpredictable because anyone who obtains a valid token may gain unauthorized access to a protected function.

A Pseudo-Random Number Generator (PRNG) generates values using a mathematical algorithm, an initial seed, and an internal state. Although its outputs may appear random, a weak PRNG can produce predictable sequences.

Weak Random Token Generation occurs when an application uses a predictable generator instead of a Cryptographically Secure Pseudo-Random Number Generator (CSPRNG). If a token reveals enough information about the generator's internal state, an attacker may predict future tokens and potentially take over another user's account.

The Vulnerable Code



      

        Highlighted:
        The vulnerable implementation uses a Linear Congruential
        Generator (LCG). Each new state is calculated from the
        previous state using a known mathematical formula.
        When the token directly exposes the internal state,
        an attacker can calculate the next token.
      


      

          The generated token is only 32 bits long. However, the main vulnerability is the predictable LCG algorithm, not just the token length. 
          Even increasing the token length would not make this generator cryptographically secure.

Why it matters


      

        Predictable password reset tokens can lead to
        account takeover.
        An attacker may calculate another user's reset token
        without knowing their password.
      


      

        Attack scenario:
        The attacker requests a password reset token
        for their own account and observes the generated value.
        If the generator is predictable and the next token
        belongs to the victim, the attacker may calculate
        that token and use it to reset the victim's password.
      


      

        Guessable seeds:
        Using the current timestamp as a seed can also
        be dangerous.
        If an attacker knows approximately when a token
        was generated, they may only need to test
        a small range of possible seeds.
      


      

        Hashing does not solve predictability:
        Hashing a predictable value does not automatically
        make it unpredictable.
        If an attacker can determine the original input,
        they can calculate its hash as well.
      


      

        Real-world examples:
        The Debian OpenSSL vulnerability (CVE-2008-0166)
        reduced the number of possible cryptographic keys.
        Android's 2013 SecureRandom issue also demonstrated
        the consequences of weak randomness in
        security-sensitive operations.
      


    



    
    


      
The fix


      

        Security-sensitive tokens must be generated using
        a Cryptographically Secure Pseudo-Random Number
        Generator (CSPRNG).
      


      



      

        Highlighted:
        The secure implementation uses
        crypto.getRandomValues()
        to generate cryptographically secure random bytes
        instead of calculating tokens from
        a predictable LCG state.
      


      
Additional Security Recommendations

      

        Security-sensitive tokens should contain at least
        128 bits of unpredictable randomness,
        expire after a limited period,
        and be valid for only one use.
      


      

        Password reset tokens should be stored securely,
        preferably as hashes, and reset requests
        should be rate-limited to reduce abuse.
