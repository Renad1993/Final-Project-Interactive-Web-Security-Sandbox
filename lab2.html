Weak Random Token Generation

OWASP A02:2021 CWE-330 | CWE-338

What it is

Applications use secret tokens for password resets, session IDs, invitation codes, and API keys, which must be unpredictable to prevent unauthorized access.

Weak Random Token Generation occurs when these tokens are created using a predictable Pseudo-Random Number Generator (PRNG) instead of a Cryptographically Secure PRNG (CSPRNG).

Since weak PRNGs may produce predictable sequences, attackers can potentially infer the generator's internal state from its outputs and use it to predict future tokens.

The Line



      

        Highlighted:
        The vulnerable implementation uses a Linear Congruential
        Generator (LCG). Each new state is calculated from the
        previous state using a known mathematical formula.
        When the token directly exposes the internal state,
        an attacker can calculate the next token.
      


      

          The generated token is only 32 bits long. However, the main vulnerability is the predictable LCG algorithm, not just the token length. 
          Even increasing the token length would not make this generator cryptographically secure.

Why it matters


      

       One predicted password-reset token can be enough to take over a victim's account without knowing their password. This can expose private data, 
       allow unauthorized actions, and compromise account security.
      


      

        Real-world case:
         In 2008, the Debian OpenSSL vulnerability (CVE-2008-0166) revealed that weak randomness had made cryptographic keys predictable, putting 
         affected systems at risk of unauthorized access.
      


    


    
    


      
The fix


      

        Security-sensitive tokens must be generated using
        a Cryptographically Secure Pseudo-Random Number
        Generator (CSPRNG).
      


      



      

        Highlighted:
        The secure implementation uses
        crypto.getRandomValues()
        to generate cryptographically secure random bytes
        instead of calculating tokens from
        a predictable LCG state.
      


      
Additional Security Recommendations

      

        Security-sensitive tokens should contain at least
        128 bits of unpredictable randomness,
        expire after a limited period,
        and be valid for only one use.
      


      

        Password reset tokens should be stored securely,
        preferably as hashes, and reset requests
        should be rate-limited to reduce abuse.
