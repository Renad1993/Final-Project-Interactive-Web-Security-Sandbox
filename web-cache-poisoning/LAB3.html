Web Cache Poisoning

Understand the vulnerability through an interactive demonstration.

01 / UNDERSTAND

What is Web Cache Poisoning?

Web Cache Poisoning is a vulnerability that occurs when a website stores a manipulated response in its cache. This can happen when the cache does not correctly consider all the request information that affects the response.

How does it happen?

An application may use an HTTP header, such as X-Forwarded-Host, to generate a response. If the cache ignores that header when identifying cached content, an unexpected response may be stored and served to other visitors.

Why is it dangerous?

Visitors may receive manipulated content instead of the expected website content. Depending on the application, this can cause misleading pages, incorrect links, or other security problems.

OWASP A06:2025 – Insecure Design
CWE CWE-436 – Interpretation Conflict
CAPEC CAPEC-141 – Cache Poisoning

Note: These classifications are related references. The exact classification depends on the vulnerability scenario.

02 / CODE ANALYSIS

Vulnerable Code vs Fixed Code

Compare the vulnerable implementation with the secure version to understand how the issue is introduced and fixed.

01

Vulnerable Code

VULNERABLE

The application uses an untrusted HTTP header to generate a response, but the cache key does not account for that header. 

const cache = new Map();

function getPage(request) {

  const host =
    request.headers["x-forwarded-host"];

  const cacheKey = "/home";

  if (cache.has(cacheKey)) {
    return cache.get(cacheKey);
  }

  const response = {
    website: host
  };

  cache.set(cacheKey, response);

  return response;
}
Problem:

The cache uses the same key for different host values. This can cause a manipulated response to be reused for other visitors.

02

Fixed Code

FIXED

The application uses a trusted host instead of accepting an untrusted host value from the request. 

const cache = new Map();

const TRUSTED_HOST =
  "techstore.example";

function getPage(request) {

  const host = TRUSTED_HOST;

  const cacheKey = "/home|" + host;

  if (cache.has(cacheKey)) {
    return cache.get(cacheKey);
  }

  const response = {
    website: host
  };

  cache.set(cacheKey, response);

  return response;
}
Solution:

The application uses a trusted host and a consistent cache key, preventing an untrusted header from controlling the generated response.

KEY DIFFERENCE: The vulnerable version trusts an untrusted header. The fixed version uses a trusted host value.
